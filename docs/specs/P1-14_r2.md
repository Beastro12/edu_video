# Spec — P1-14 round 2 (and P3-4 round 2): Ctrl-C never interrupts the pool's own machinery

Worktree: wt/p1-14 (branch wt/p1-14, now 2ab8998 P1-14 r1, then 84a1642 P3-4 r1). Add NEW

## Why (review a08ee, reproduced by the orchestrator)
- **C1.**
  - CPython 3.11's `ThreadPoolExecutor._adjust_thread_count` runs `t.start()` (thread.py:199)
    and only then `self._threads.add(t)` (:200).
  - `Thread.start()` blocks in an interruptible `self._started.wait()` (threading.py:969).
  - A Ctrl-C there leaves a started worker that `shutdown(wait=True)` never joins.
  - `finally` then clears both flags while that worker makes paid calls with no attribution.
  - The orchestrator ran `p1-14-review/p1_orphan_thread.py`: 0.00 s, flags clear, a thread
    still running, "clip bought" plus a second paid call, and no film/run on either entry.
- **C2 (pre-existing).**
  - After a worker failure, the main thread waits in `pool.shutdown(wait=True)` for jobs in
    flight. A Veo job can hold that wait for up to 10 minutes.
  - A Ctrl-C there leaves `finally` without setting `interrupted`. The process exits, and the
    Veo job's "assumed billed" record never runs.
  - The orchestrator ran `p1_exit_loses_veo.py`: case A gives no ledger entry; control C gives
    "assumed billed".
  - The ledger then undercounts a billed clip, so the budget and `VEO_MAX_PER_DAY` can be
    passed. That is a CLAUDE.md hard rule.
- **W4 (pre-existing, folded in, the same class).** With WORKERS=1, or a phase of one item, a
  Ctrl-C during the Veo poll is never recorded: ai_video.py:99 catches `Exception`, not
  `KeyboardInterrupt`.

**Root cause:** an asynchronous KeyboardInterrupt raised inside concurrent.futures and threading
internals. No arrangement of try/finally around them is safe.

## Design (binding)
1. **SIGINT handler.** While `in_parallel`'s parallel path runs on the main thread, install a
   handler that only records the press. It sets `ledger.stopping` and `ledger.interrupted` and a
   local "pressed" flag, and it never raises.
   - Restore the previous handler in `finally`.
   - Off the main thread, `signal.signal` raises ValueError: keep today's behaviour there and
     say so in the docstring.
2. **Submission.** Submit in a loop that checks "pressed" before each `submit`. On a press, stop
   submitting.
3. **Waiting.** Replace the single blocking `wait` with a loop:
   `wait(futures, timeout=config.PARALLEL_POLL_S, return_when=FIRST_EXCEPTION)`.
   - Add `PARALLEL_POLL_S = 0.2` to config.
   - Each turn checks "pressed" and the first exception.
4. **On a press:**
   - `_stop(futures, interrupt=True)`: cancel what is queued, then set the flags.
   - Print one line: `• stopping: waiting for N calls in flight (they are paid for and will be
     kept)`.
   - Wait for the futures themselves, not `Thread.join`.
   - Then raise KeyboardInterrupt.
5. **On a worker failure:** today's behaviour, i.e. `stopping` only, wait for the jobs in flight,
   re-raise. The handler stays installed through that wait. A press during it sets `interrupted`
   too, so a Veo poll gives up and records "assumed billed". This is C2.
6. **Shutdown.**
   - `pool.shutdown(wait=True, cancel_futures=True)` runs with the handler still installed, so a
     press there only sets flags.
   - The flags are cleared after shutdown and after the handler is restored, on every path.
   - A second press is harmless. W2's "flags left set" path is gone.
7. **The sequential path (WORKERS<=1, or one item)** stays without a handler. W4 is fixed at its
   source instead: ai_video.py's poll records "lost track of job; assumed billed" under
   `except BaseException`, then re-raises. Fix the comment at pipeline.py:502.

## Design-check changes (Opus a08ee, 2026-10-26). Binding; they override the Design and the table above.
Probe: p1-14-review/p1r2_handler_event_deadlock.py. The orchestrator reran it and got both
results: a record-only handler doesn't shorten a timed wait (0.500 s), and a handler calling
`Event.set()` while the main thread is inside `clear()` deadlocks.

- **E1 (design 1): the handler never takes a lock the main thread may hold.**
  - It appends to a plain list.
  - It sets `ledger.stopping` and `ledger.interrupted` only while a plain bool guard is down.
  - `in_parallel` raises that guard around its own `.set()`/`.clear()` of those Events (in
    `_stop` and in the final clear). When a guarded section ends and a press was recorded, the
    main thread sets both flags itself.
  - The guard is race-free: handlers run on the main thread, between bytecodes.
- **E2 (design 1): when to install.**
  - Only if `threading.current_thread() is threading.main_thread()` AND
    `signal.getsignal(SIGINT) is signal.default_int_handler` (asyncio.Runner's rule). Otherwise
    install nothing and keep today's behaviour: SIG_IGN under nohup, a custom handler, or a C
    handler.
  - Install BEFORE the `try`, since a pending press can raise from the install itself.
  - Restore to `default_int_handler`.
- **E3 (design 6): the end order, and a press is never swallowed.**
  1. shutdown;
  2. raise the guard for good, so the handler only records from here on;
  3. clear the flags;
  4. restore the handler;
  5. if a press was recorded at ANY point, raise KeyboardInterrupt, with the precedence in E4.
  - Never clear after restoring.
  - Never return normally after a press: a press as the last future finishes must still stop the
    next, paid phase.
- **E4 (design 4/5, and table row C2's "Raises"): whichever comes first wins.**
  - **Press first → KeyboardInterrupt.** Jobs that then fail BECAUSE of the press
    (BudgetExceeded "the run is stopping", a Veo "interrupted") are never re-raised.
  - **Worker failure first, then a press → re-raise the worker's exception** with
    `e.add_note("Ctrl-C pressed while waiting for N calls in flight")`. The run report then
    doesn't advise "rerun to resume" after a budget stop.
- **E5 (design 4): the message.**
  - `• stopping: waiting for N calls in flight to finish (a Veo job gives up and is counted as
    paid)`.
  - Print a similar line on the worker-failure wait.
  - **Orchestrator decision, option (a):** a second press is harmless. The hard escape is Ctrl-\
    (SIGQUIT), documented in README's run notes as "kills at once; calls in flight are not
    recorded in the ledger". There is no third-press escape, because it would lose ledger
    entries.
- **E6 (table): add or fix these rows**, each tested with `signal.raise_signal(SIGINT)` or
  `signal.pthread_kill(main_ident, SIGINT)`.

  | Row | What must hold | How to test |
  |---|---|---|
  | A press pending when the handler is installed (replaces "before the pool exists") | KeyboardInterrupt from the install; no pool; flags clear | patch `pipeline.signal.signal` to raise the signal, then call the real one |
  | A press inside `ThreadPoolExecutor()` | no submit at all | |
  | A press as the last future finishes, or during result collection | KeyboardInterrupt, not a return | the last job `pthread_kill`s the main thread before returning |
  | A press while the main thread is inside `_stop`'s or the final clear's Event calls | no deadlock | an Event subclass whose `set` raises the signal while holding `_cond`, in a child process with a watchdog |
  | A press during the handler restore | KeyboardInterrupt | |
  | A press first, then jobs fail because of it | KeyboardInterrupt | |
  | SIGINT is SIG_IGN or a custom handler | nothing installed; a press does what it did; the handler is unchanged after | |
  | A KeyboardInterrupt raised as an exception (r1's `SubmitInterrupted`) | r1's fallback: both flags, cancel, wait, re-raise | keep the `except KeyboardInterrupt` |

  - Rename "a second press during shutdown" to "a second press while waiting for calls in flight

  - "Off the main thread": docstring only, plus a test that no handler is installed.
