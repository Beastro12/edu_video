# Spec — P0-9: the Veo start POST is retried after a timeout (D11 broken)

Found by design checker ab947 (P3-10 design check). Reproduced by the orchestrator with
`probes/design-p3-9-10/scripts/probe_veo_start_timeout.py`: a ReadTimeout and then a 200 gave
2 start POSTs.

## The bug (verified)
- `google_client.start_job_options()` sets
  `HttpRetryOptions(attempts=MAX_RETRIES+1, http_status_codes=[429])`.
- google-genai 2.25.0's retry predicate (`_api_client.py:575-578`) retries on
  `isinstance(e, _HTTPX_TRANSIENT_EXC)` WHATEVER the code list says. That tuple
  (`_api_client.py:111-117`) is httpx/httpx2 `TimeoutException` and `ConnectError`.
- So a start POST that times out after Google accepted the job is sent again: a second job,
  billed (about €2.94, D20).
- The SDK swallowed the first timeout, so `ai_video._buy`'s `except (ServerError,
  TimeoutException)` "may have started" record (ai_video.py:82-89) never runs. The ledger counts
  one job and Google bills two. Both the budget and `VEO_MAX_PER_DAY` (a CLAUDE.md hard rule)
  undercount.
- D11 says: "The POST that starts a Veo job is retried only on 429 … a retry would start and
  bill a second one."
- No test covered this: `test_retries.py:202-211` tries only `[503, 200]` and `[429, 429, 400]`.

## Accept
1. The start POST is never retried by the SDK: `start_job_options()` gives `attempts=1`.
2. A 429 on the start is retried by our own code, which never retries anything else. A 429 means
   Google refused the job, so a retry cannot bill twice. Use `retries.call` with a narrow
   predicate, or a small loop with the same backoff settings. Its wait and log lines follow
   retries.call's.
3. A timeout or 5xx on the start: exactly 1 POST, the existing "may have started" ledger entry,
   and the exception propagates (D10, D11). A ConnectError means the request never left, so it
   gets no record. ConnectTimeout is a TimeoutException, so it keeps the conservative record;
   say so in the code.
4. Polling (`operations.get`) and the download keep their retries. They are reads, and a retry
   costs nothing.

## Tests (D30's rule: the real SDK with its OWN httpx client, `httpx.HTTPTransport.handle_request` faked, a socket guard)
- ReadTimeout on the first start POST: exactly 1 POST, 1 ledger entry ("may have started"),
  raises. This fails on base, which makes 2 POSTs.
- 429, then 200: 2 POSTs, 1 job, 1 normal ledger entry.
- 503: 1 POST, 1 "may have started" entry, raises.
- ConnectError: 1 attempt, no ledger entry, raises.
- Polling with a 503 on one `operations.get`: retried, and the clip is recorded once.
- Keep test_retries' existing two cases passing, or update them with a reason.

## Invariants
- No paid cache key changes (D9).
- `google_client.make()`'s arguments are unchanged, for stills and the rest; P3-10 touches it next.
- The daily cap check under `_veo_lock` is unchanged.

## DECISIONS
- Amend D11 with the finding: the SDK retries transport timeouts and connect errors whatever its
  status-code list says, so the start makes one attempt and our code retries 429 only.
- Measured on google-genai 2.25.0. A test pins it, so an SDK upgrade that changes the predicate
  is noticed.

**Fast subset:** `pytest -q tests/test_retries.py tests/test_veo_cap.py tests/test_budget.py tests/test_parallel.py`.

## Design-check changes (Opus ab947, 2026-10-26). Binding; they override anything above.
Probe: scratchpad/probes/design-p0-9/scripts/probe_p09.py (output in probe_p09.out).
1. **Accept 1:** `start_job_options()` returns
   `HttpOptions(retry_options=HttpRetryOptions(attempts=1))`.
   - An `HttpOptions()` WITHOUT retry_options falls back to the client's own loop, which retries
     5xx (`_api_client.py:1532`).
   - The 503 test pins this.
2. **Accept 2:**
   - `retries.call` gains `transient: Callable[[BaseException], bool] = is_transient`.
   - The start passes `lambda e: isinstance(e, errors.ClientError) and e.code == 429`.
   - The callable wraps ONLY `client.models.generate_videos(...)`; the ledger record sits outside
     the loop.
   - `retries.call` unchanged around the start would retry 5xx and timeouts (`retries.py:40-49`)
     and start a second job (probed).
   - Also binding:
     - check `ledger.interrupted` before each 429 retry, so a Ctrl-C never starts a new job;
     - honour a `Retry-After` header if present (`retries.retry_after_s`).
3. **Accept 3, replacing the ConnectError sentence:** every exception from the start is recorded
   as "may have started" and re-raised, except those that prove nothing was sent or the job was
   refused:
   - `httpx.ConnectError`, `httpx.ProxyError` and `httpx.PoolTimeout`: raised before any request
     byte is written, httpcore 1.0.9 (`_backends/sync.py:150-153`, `:202-205`,
     `_sync/http_proxy.py:297`, `:315-316`);
   - `errors.ClientError`: 4xx, refused.
   This covers ServerError, ReadTimeout, WriteTimeout, ReadError, WriteError,
   RemoteProtocolError and an unparseable 200, all of which today's code fails to record (on base
   too).
   - **ConnectTimeout (orchestrator decision): still recorded**, the conservative choice. A false
     record costs budget headroom and one daily clip, never real money; a missed one can. The code
     comment says so, and cites the httpcore evidence that it is in fact pre-send.
4. **Tests (add):**
   - RemoteProtocolError on the start, and separately ReadError: each gives 1 POST, 1 "may have
     started" entry, and raises.
   - 429 five times: 5 POSTs (up to MAX_RETRIES+1), no ledger entry, ClientError raised.
   - A press (`ledger.interrupted` set) during the 429 backoff: no further POST.
   - An SDK pin: with today's options (`http_status_codes=[429]`, attempts > 1), a ReadTimeout
     gives 2 POSTs. This is the "noticed on upgrade" test.
   - Test setup:
     - patch `ai_video.time.sleep` (the 10 s poll);
     - set `RETRY_BASE_S`, `RETRY_JITTER_S` and `RETRY_MAX_S` tiny;
     - count POSTs by the `:predictLongRunning` path.
   - test_retries.py:202-211 passes unchanged.
5. **DECISIONS (D11 amendment):** a start that fails after the request may have left is recorded
   whatever the error type. ConnectError, ProxyError and PoolTimeout are provably pre-send.
   ConnectTimeout is recorded anyway, on purpose.
