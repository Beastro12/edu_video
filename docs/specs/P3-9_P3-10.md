## P3-9 — The build remembers whether Veo is allowed (planning group N6)

**From BACKLOG.**
- `allow_veo = ai_video.available() and not args.no_ai_video` (pipeline.py:569). Veo is on
  whenever a Google key is set.
- A rerun that leaves out `--no-ai-video` can therefore buy Veo clips (about €2.94 each, D20)
  that nobody asked for. The pilot flow (P3-7) prints `--no-ai-video` on every command, but a
  hand-typed rerun is one missing flag away from spending.

**Accept (BACKLOG P3-9):**
- Like the style (D25), `build/<slug>/` records whether Veo is allowed.
- A rerun without a flag keeps the recorded choice and prints it.
- A new `--ai-video` flag and the existing `--no-ai-video` each switch the choice, with a line
  saying so.
- `--estimate` honours the record.
- Tests: a rerun after `--no-ai-video` requests no Veo; an explicit `--ai-video` does.

**Design (mirror the style record exactly; read pipeline.py:94-122 first):**
- `config.VEO_FILE = "ai_video"`, holding `on` or `off` plus a newline.
- `_recorded_veo(work) -> str | None`:
  - None if the file is missing;
  - `ValueError` naming the file and "fix or delete the file" if its text isn't `on` or `off`;
  - main turns the ValueError into `ap.error`, like the style.
- `pick_veo(flag, recorded) -> tuple[str, str]` returns (choice, source):
  - `--ai-video` gives `on` and `--no-ai-video` gives `off`, each with "--ai-video" /
    "--no-ai-video" as the source;
  - otherwise the record, with source "recorded in the build";
  - otherwise `on`, with source "default". Today's default is unchanged; changing it is
    Pietro's decision 3 (PLAN), not this task's.
- `--ai-video` and `--no-ai-video` are a mutually exclusive argparse group.
- `allow_veo = ai_video.available() and choice == "on"`.
- Print one line, before the estimate, in the style line's format:
  `• ai video: on (default)` / `off (recorded in the build)` / `off (--no-ai-video)`.
  - When the choice is `on` but no Google key is set, add "; no GOOGLE_API_KEY, so stills are
    used".
  - When the flag changes a recorded choice, print a second line, like the style's:
    `• ai video: this build is recorded as off; this run turns it on (--ai-video)`.
- `_record_veo(work)` writes the CHOICE (not availability):
  - via `_write_text` (atomic), at the same point and under the same guard as `_record_style`:
    inside the `recording` block, before the script stage, only when `_brief_conflict(...)` is
    None;
  - only if the record differs from the choice, so an unchanged record is never rewritten.
- `--estimate` reads the record and the flags in the same way, and writes nothing.
- `run_report.py`:
  - `_veo_off` (run_report.py:180) gives the actual reason: "--no-ai-video", "recorded in the
    build (rerun with --ai-video to allow it)" or "no GOOGLE_API_KEY". Pass the source into the
    report, e.g. as `recording(..., veo_source=...)`, or put it on `run`.
  - The next-steps fix text at run_report.py:357 ("rerun without it to use Veo") becomes "rerun
    with --ai-video to use Veo (it costs money)" when the choice was off.
- `--help`: `--no-ai-video` says "skip Veo and use stills; the build remembers it". `--ai-video`
  says "allow Veo again on a build that recorded --no-ai-video (it costs money)".
- README's run lines and the pilot tool's printed commands keep `--no-ai-video`: it is harmless
  and explicit.

**Invariants:**
- `build/<slug>/ai_video`:
  - written only by `_record_veo`, atomically, on a non-estimate run that is not refused;
  - read by main (on every run and the estimate) and by the run report.
- An explicit flag always wins, and the record follows it.
- No paid cache key changes (D9): the record is a new, free file, and Veo, still and Manim paths
  don't depend on it.
- A build made before P3-9 (no record) behaves exactly as today.

**Acceptance scenarios (tests, in a new tests/test_veo_record.py; providers faked; count Veo
start requests, i.e. `generate_videos` calls):**
1. A run with `--no-ai-video` writes `off`. A rerun with no flag makes 0 Veo requests and prints
   `off (recorded in the build)`. Its estimate shows no Veo cost.
2. On that build, `--ai-video` makes Veo requests for the ai_video scenes, prints the switch line,
   and the record becomes `on`.
3. A fresh build with no flag and a Google key behaves as today: Veo is requested, and the
   record is `on`.
4. `--estimate --no-ai-video` on a fresh build writes no record and creates no build folder
   (today's estimate writes nothing).
5. A record holding `maybe` gives an argparse error naming the file, and nothing is written.
6. `--ai-video --no-ai-video` gives an argparse error.
7. A run refused for a brief conflict writes no record.
8. A run stopped in the script stage (e.g. a fake writer that raises) keeps the record it wrote.
9. An unchanged record is not rewritten: its bytes and mtime are the same after a rerun.
10. Run report: after scenario 1's rerun, the report's Veo line says "recorded in the build", and
    its next step says "--ai-video".
11. `--ai-video` with no Google key: the record is `on`, 0 Veo requests, and the printed line
    says stills are used.

**Pinned tests to update:** tests/test_run_report.py and tests/test_style.py mention
`no_ai_video` / `_veo_off`. Update the expected strings only where the wording changes, and list
each change in the report.

**DECISIONS:** D25 (the pattern), D20 (the Veo cost), D10. Propose a new entry: "The build records
whether Veo is allowed (P3-9)".
**Fast subset:** `pytest -q tests/test_veo_record.py tests/test_style.py tests/test_run_report.py tests/test_budget.py`.

## P3-10 — Record redacted live responses as contract fixtures (planning group N2)

**Why:**
- Every provider is faked offline.
- What the fakes return is the implementers' reading of each provider's docs, never a real
  response. Several shapes are unverified:
  - ElevenLabs error bodies (P3-6 ASSUMED);
  - Gemini image `parts`;
  - Veo operations;
  - Claude's forced-tool response.
- The first live calls should pay once to capture the real shapes. After that the offline tests
  can replay them through the real parsing code.

**Accept (BACKLOG P3-10):**
- With `RECORD_LIVE=1`, every provider response is saved under `build/recorded/`, redacted:
  keys and headers removed, binary bodies stored as hash, length and head.
- `tests/test_contract.py` replays fixtures put into `tests/fixtures/live/` through the real
  parsing code, and skips when there are none.
- A test proves that no key string appears in any saved file.
- `make smoke` with `RECORD_LIVE=1` then pays once for real fixtures.

**Design:**
- A new module `recorder.py` at the repo root, beside ledger.py and retries.py.
  - `config.RECORD_LIVE = os.getenv("RECORD_LIVE") == "1"` and
    `config.RECORDED_DIR = "build/recorded"`.
  - `recorder.httpx_hooks()` returns `{"response": [hook]}`, or `{}` when off.
  - `recorder.requests_hooks()` returns `{"response": [hook]}`, or `{}` when off.
- **Where it hooks (one place per HTTP stack; nothing else changes behaviour):**
  - **Anthropic:** `llm.make_client(**kwargs)` passes
    `http_client=anthropic.DefaultHttpxClient(event_hooks=recorder.httpx_hooks())` when recording
    is on. DefaultHttpxClient keeps the SDK's own timeouts and limits; a plain httpx.Client would
    not. This covers `_client` and P3-6's preflight client if that is built by `make_client`.
    Check it, and route it through `make_client` if not.
  - **Google:** `google_client.make(httpx_client=None)`. When recording is on and no client is
    given, it passes an `httpx.Client` with the hooks.
    - Trap to check: does google-genai still apply `HttpOptions.timeout` and retry_options when
      an `httpx_client` is passed? Read the installed SDK
      (`.venv/lib/python3.11/site-packages/google/genai/_api_client.py`). If it doesn't, set the
      same timeout on the httpx client, and state what you found.
    - This covers stills, the still critic (if Google), Veo starts, polls and downloads, and
      preflight's `models.get`.
  - **ElevenLabs:** every `requests.*` call in agents/voice.py and scripts/preflight.py gets
    `hooks=recorder.requests_hooks()`.
- **Saved file:** one JSON per response, written atomically (`utils.save_json` or
  `atomic_output`), at
  `build/recorded/<provider>/<UTC yyyymmddThhmmss>-<pid>-<counter>-<method>-<path-slug>.json`.
  - `provider` is `anthropic`, `google` or `elevenlabs`, taken from the host.
  - The counter is process-wide and taken under a lock, because in_parallel runs threads.
  - The file holds:
    - `provider`, `method`, the redacted URL and `status`;
    - an allowlist of response headers: `content-type`, `content-length`, `request-id`,
      `x-request-id`, `retry-after`, plus any `ratelimit` header names with their values;
    - `request`: the JSON body, compacted (below) and redacted, or `null` when the body isn't
      JSON;
    - `response`: the JSON body, compacted and redacted, or a binary stub for a non-JSON body.
- **Binary stub:**
  `{"__binary__": {"sha256": …, "length": n, "head_b64": base64(first 32 bytes), "content_type": …}}`.
  - Used for a non-JSON body (audio/mpeg, image/*, video/*, application/octet-stream).
  - Also used for any JSON string value of 512 or more characters that is entirely base64
    alphabet (Gemini `inline_data.data`, Claude image inputs). Ordinary text has spaces, so it
    never matches. Test that.
- **Redaction (two layers):**
  1. Structural:
     - drop every request header (none are saved);
     - remove the query parameters `key`, `api_key`, `xi-api-key` and `access_token` from the
       URL, along with any parameter whose value is a configured secret;
     - replace the voice ID in ElevenLabs paths with `<voice_id>` (orchestrator decision: it
       names the owner's voice).
  2. Value scan: before writing, serialize the record and replace every occurrence of each
     configured secret (`ANTHROPIC_API_KEY`, `ELEVENLABS_API_KEY`, `GOOGLE_API_KEY`, and the
     voice ID) with `<redacted>`. Also replace the secret's URL-encoded and base64 forms.
     Secrets shorter than 8 characters are skipped, so a test dummy like "x" can't blank
     ordinary text; say so.
  - Secrets are read from `config` at write time, never printed, never logged.
- **Failure is never fatal:** any exception inside the hook prints one line,
  `• recorder: could not save <provider> response (<ExceptionType>)`, and the call goes on. The
  hook must not consume a streaming body the caller still needs: call `response.read()`, and
  show it in a test that the SDK still parses the response after the hook ran.
- **Off by default:** when `RECORD_LIVE` is not `1`, no hook is installed, and the clients are
  built exactly as today. Pin this: `make_client()` and `google_client.make()` get the same
  arguments as at base.
- **tests/test_contract.py:** replays each fixture in `tests/fixtures/live/<provider>/*.json`
  through the real parsing path, with the transport mocked:
  - Anthropic: an `anthropic.Anthropic` client on an `httpx.MockTransport` that serves the
    fixture → `llm.structured` (or `_create`) returns the tool input, and `ledger.record` gets
    the usage numbers;
  - Google image: genai on a MockTransport → `image_agent._buy`'s parsing finds the image. Use
    synthetic bytes for the binary stub: the recorded `head_b64` padded to `length` (cap 1 MB),
    so magic-byte checks pass;
  - Veo: the start, poll and download sequence;
  - ElevenLabs: `voice._buy`, and preflight's subscription, voice and error parsing.
  - With no fixtures for a provider, its tests skip with a reason that names the folder.
  - Fixtures are matched to a parser by method and path pattern, which is written down in the
    test file.
- **Making fixtures:** README gets one paragraph:
  - `RECORD_LIVE=1 make smoke`, optionally plus a `scripts/preflight.py` run;
  - then copy chosen files from `build/recorded/` into `tests/fixtures/live/<provider>/`, and
    review each one before committing;
  - `build/` is git-ignored, so recordings are never committed by accident.

**Invariants:**
- No saved file contains any configured secret, in plain, URL-encoded or base64 form.
- No request header is ever saved.
- With `RECORD_LIVE` unset:
  - zero files are written under `build/recorded/`;
  - the client construction is byte-identical in arguments to base.
- No paid call is added, and no call is retried because of the recorder.
- No paid cache key changes (D9).

**Acceptance scenarios (tests/test_recorder.py; all offline, httpx.MockTransport and a requests
mock):**
1. `RECORD_LIVE=1`, with dummy secrets of 20 or more characters. Fake providers echo:
   - the key in a response header;
   - the key in the URL query (`?key=…`);
   - the key inside an error message in the JSON body;
   - the key base64-encoded in a body field.
   After calls through each of the three stacks, no file under `build/recorded/` contains any
   secret in any of the three forms. Grep the bytes.
2. A binary response (fake mp3 bytes) is saved as a stub with the right sha256, length and head,
   and the caller still gets the full bytes.
3. A Gemini-like JSON with a 100 kB base64 `data` field is saved compacted, and ordinary long
   text is kept.
4. A hook that raises (e.g. the directory can't be written) prints the one line, and the SDK
   call still returns its parsed result.
5. Recording off: nothing is written, and the client factories get the base arguments.
6. Eight threads making calls at once give eight distinct files, none partial.
7. The SDK still parses a response after the hook has read it (Anthropic and google-genai).
8. tests/test_contract.py with an empty `tests/fixtures/live/` skips everything. With one
   synthetic fixture per provider (made by the recorder in scenario 1 and copied by the test into
   a temp fixtures dir), it passes. Monkeypatch the fixtures path.

**DECISIONS:** D10, D11 (no added retries or paid calls), D9. Propose a new entry: "Live responses
are recorded, redacted, only on request (P3-10)".
**Fast subset:** `pytest -q tests/test_recorder.py tests/test_contract.py tests/test_preflight.py tests/test_live_optin.py`.

### P3-10 (starts after P0-9 merges: both touch google_client.py)
1. **Google client: `client_args`, not `httpx_client`.**
   - Pass `client_args={"event_hooks": recorder.httpx_hooks("google")}` in `HttpOptions`, never
     `httpx_client`. A client the caller gives (tests) is left alone.
   - Why (measured): with `httpx_client` the SDK's `SyncHttpxClient` is replaced, which loses
     `follow_redirects=True`. A redirecting download then raises `APIError 302`, and a Veo clip
     that is already recorded as spent is lost. It also leaks a client per `make()`, and makes
     D30's bug class invisible.
   - Record in DECISIONS: retry and timeout survive `httpx_client`; redirects and `close()` don't.
2. **The hook.**
   - It calls `response.read()` (requests: `r.content`) FIRST, outside any `try`, so a read
     error propagates unchanged and the SDK's retry sees it.
   - Parsing, compaction, redaction and the write are inside `except Exception` and print one
     line through `utils.log`.
   - It returns None and accepts `**kwargs`.
3. **requests.** Use `requests.post(..., **recorder.requests_kwargs("elevenlabs"))`, which gives
   `{}` when recording is off. Pin that, with recording off, the post gets exactly
   `url, headers, json, timeout`, so no fake with a fixed signature breaks.
4. **Provider:** bound when the hook is made, not taken from the host.
5. **URLs and file names.**
   - Keep only allowlisted query names (`alt`, `output_format`); every other value becomes
     `<redacted>`.
   - The file name's slug is built from the REDACTED path, so the voice ID never reaches a file
     name.
   - Add a test: no file name under build/recorded contains a secret.
6. **Anthropic client.**
   - `make_client`: `anthropic.Anthropic(**{"api_key": …, "max_retries": config.MAX_RETRIES,
     **recording, **kwargs})`.
   - `recording` is the hooked `http_client`, given only when recording is on and the caller
     passed no `http_client`.
   - Route `preflight._anthropic_client` through `make_client(max_retries=0,
     timeout=config.PREFLIGHT_TIMEOUT_S)`.
   - Anthropic tests use httpx2 (this SDK runs on httpx2).
   - The hook is duck-typed, and names exceptions from both httpx packages.
7. **Where and when.**
   - Write to `Path(config.BUILD_DIR) / "recorded"` at write time (D10: build/ is anchored).
   - conftest sets `config.RECORD_LIVE = False` for offline tests, so an exported RECORD_LIVE=1
     cannot change `make check`.
8. **Replay.**
   - Replay goes below the SDK: `httpx.HTTPTransport.handle_request`,
     `httpx2.HTTPTransport.handle_request` and `requests.adapters.HTTPAdapter.send`, under a socket
     guard.
   - conftest gains a saved original for `Models.retrieve`, and a way to lift its requests guard
     for replay.
   - A base64 stub carries `"encoding": "base64"`, with its statistics over the decoded bytes.
   - The image fixture's payload is a real tiny image of the recorded MIME type, because
     `_buy` runs FFmpeg on non-PNG bytes.
   - The Veo replay patches the 10 s poll sleep and links the redirect chain.
9. **README and PLAN.**
   - Say what each source records:
     - smoke: Claude (writer, critic, still critic), ElevenLabs 200s, Gemini images;
     - preflight: model GETs and ElevenLabs bodies;
     - Veo only through a paid Veo run. Never suggest one just for fixtures.
   - Set `RECORD_LIVE=1` on the FIRST smoke and preflight of the resume protocol (PLAN step 3:
     a second smoke re-buys everything).
10. **Added scenarios:**
    - A body that times out mid-read, with recording on, is retried exactly as with it off
      (Google: 2 requests, success).
    - A write failure inside the Veo start's hook still returns the operation, and the ledger
      gets exactly 1 Veo entry.
    - One path per provider through the SDK's own client with the transport faked (D30), with
      the hooks firing.
    - No file name under build/recorded contains a secret.
11. **Suggestions taken:**
    - scan base64 at all 3 alignments, standard and urlsafe, and the `strip()`ped form;
    - search the raw body for secrets before stubbing, and blank the stub's head on a hit;
    - keep redacted non-JSON text bodies up to 2 kB;
    - don't hook preflight's host GETs;
    - pin that the paid cache keys are unchanged with RECORD_LIVE=1.
